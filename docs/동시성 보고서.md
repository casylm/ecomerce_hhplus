# 동시성 문제 분석 및 해결 보고서

## 1. 개요

본 보고서는 이커머스 시스템에서 발생할 수 있는 동시성 문제를 식별하고, 각 도메인별로 적절한 락(Lock) 전략을 적용하여 해결한 내용을 다룹니다.

---

## 2. 서비스에서 발생 가능한 동시성 문제

### 2.1 쿠폰 발급 (선착순)

**문제 사례:**
- 100명이 동시에 쿠폰 발급 요청 시, 재고가 10개라면 10명만 성공해야 함
- 동시성 제어 없이는 20명, 30명에게 잘못 발급되는 오류 발생

**원인:**
- 쿠폰의 `quantity` 컬럼을 여러 트랜잭션이 동시에 읽고, 동시에 감소시키는 **Race Condition** 발생

### 2.2 포인트 차감

**문제 사례:**
- 동일 사용자가 2번 클릭하여 결제 2건이 동시에 요청됨
- 최종 포인트가 음수가 되거나, 실제보다 더 많이 차감될 수 있음

**원인:**
- 동일 사용자의 포인트를 여러 트랜잭션이 동시에 읽고 차감하여 **Double Spend** 문제 발생

### 2.3 상품 재고 차감

**문제 사례:**
- 여러 사용자가 동일 상품 주문 시 재고가 음수로 가는 문제
- 재고보다 많은 주문이 들어오는 **Overselling** 문제 발생

**원인:**
- 상품 재고를 여러 트랜잭션이 동시에 읽고 차감하여 재고 부족 검증 실패

---

## 3. 발생 원인 분석

### 3.1 공통 원인

1. **공유 자원에 대한 동시 접근**
   - 여러 스레드(요청)가 공유 자원(쿠폰, 포인트, 상품)에 동시에 접근

2. **트랜잭션 격리 수준의 한계**
   - DB의 트랜잭션 격리 수준만으로는 해결 불가능한 업무 로직
   - JPA의 기본 `READ_COMMITTED` 수준에서는 Lost Update, Dirty Read, Non-repeatable Read 가능성 존재

3. **읽기-수정-쓰기 패턴의 취약점**
   - 서비스 단에서 "읽기 → 변경 → 쓰기" 시점에 다른 요청이 끼어듦

---

## 4. 동시성 해결 전략 선정

해결 방법은 크게 2가지를 고려했습니다:

### ✅ 낙관적 락 (Optimistic Lock)

**적용 시기:**
- 데이터 충돌이 드물지만 치명적일 때 적합
- 사용자 기반 데이터(포인트, 쿠폰 사용)

**장점:**
- 성능이 좋음 (락을 걸지 않음)
- 충돌 시 재시도 가능

**단점:**
- 충돌이 많으면 재시도 오버헤드 발생

---

### ✅ 비관적 락 (Pessimistic Lock)

**적용 시기:**
- 충돌이 자주 발생하는 자원에 적합
- 상품 재고, 선착순 쿠폰 재고

**장점:**
- 확실한 동시성 제어
- 데이터 정합성 보장

**단점:**
- 성능 저하 가능성
- 데드락 위험

---

## 5. 도메인별 해결 방안

### 5.1 선착순 쿠폰 발급 → 비관적 락 적용

**문제:**
- 쿠폰 재고는 많은 유저가 동시에 접근하는 공유 자원
- 충돌 확률이 매우 높음

**선택한 전략:**

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT c FROM Coupon c WHERE c.id = :id")
Optional<Coupon> findByIdWithLock(Long id);
```

**효과:**
- ✅ 쿠폰을 조회하는 동안 다른 트랜잭션이 재고를 수정할 수 없음
- ✅ 재고 감소가 완벽히 원자적으로 수행됨
- ✅ Overselling, 초과 발급 문제 해결

**통합 테스트 결과:**
- 재고 10개, 100명 동시 요청 → 정확히 10명만 성공
- 재고 1개, 2명 동시 요청 → 정확히 1명만 성공

---

### 5.2 사용자 포인트 차감 → 낙관적 락 적용

**문제:**
- 동일 사용자가 빠르게 두 번 결제할 때 포인트가 두 번 차감될 위험
- 여러 사용자가 같은 userId를 사용하는 일은 없음 → 충돌 빈도는 낮음

**선택한 전략:**

```java
@Version
private Long version;
```

- `@Version` 컬럼 추가
- 동시 업데이트 시 `OptimisticLockException` 발생 → 재시도 처리

**효과:**
- ✅ 동일 사용자 포인트가 동시에 수정될 때 1개만 성공
- ✅ "중복 결제" "Double Spend" 문제 해결
- ✅ 실패 시 재시도 가능

---

### 5.3 상품 재고 차감 → 비관적 락 적용

**문제:**
- 상품 재고는 매우 경쟁이 치열한 공유 자원
- 100명이 동시에 인기 상품 구매 시 초과 판매 위험이 매우 높음

**선택한 전략:**

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT p FROM Product p WHERE p.id = :id")
Optional<Product> findByIdForUpdate(Long id);
```

**효과:**
- ✅ 하나의 재고 변경이 끝날 때까지 다른 트랜잭션은 대기
- ✅ 재고 음수, Overselling 완전 방지

**통합 테스트 결과:**
- 재고 100개, 100명 동시 요청 → 정확히 재고 0개
- 재고 100개, 150명 동시 요청 → 100명 성공, 50명 실패

---

## 6. 전체 아키텍처 및 트랜잭션 흐름

### 6.1 결제 흐름에서의 락 조합

| 단계 | 자원 | 락 전략 | 이유 |
|------|------|---------|------|
| 쿠폰 사용 | `userCoupon` | 낙관적 락 | 동일 사용자 중복 사용 방지 |
| 포인트 차감 | `point` | 낙관적 락 | 재시도 가능, 충돌 적음 |
| 상품 재고 차감 | `product` | 비관적 락 | 여러 유저 동시 접근, 충돌 많음 |

### 6.2 트랜잭션 격리 수준

- **Spring 기본 설정:** `READ_COMMITTED`
- **락 적용 후:** 각 도메인별 적절한 락 메커니즘 추가

## 8. 결론

### 8.1 적용 결과

| 도메인 | 문제 | 해결 전략 | 결과 |
|--------|------|-----------|------|
| 쿠폰 발급 | 초과 발급 | 비관적 락 | ✅ 해결 |
| 포인트 차감 | 중복 차감 | 낙관적 락 | ✅ 해결 |
| 상품 재고 | Overselling | 비관적 락 | ✅ 해결 |

### 8.2 핵심 성과

1. **데이터 정합성 100% 보장**
   - 모든 동시성 테스트 통과
   - Race Condition 완전 해결

2. **도메인별 최적 전략 적용**
   - 충돌이 많은 자원 → 비관적 락
   - 충돌이 적은 자원 → 낙관적 락

3. **실전 시나리오 검증**
   - 통합 테스트로 실제 DB 환경에서 검증
   - Testcontainers를 활용한 MySQL 환경 테스트

## 9. 향후 개선 방안

### 9.1 Redis 분산 락 고려

현재는 DB 락을 사용하지만, 트래픽이 증가하면 Redis 기반 분산 락 고려:
- Redisson의 `RLock`
- Lettuce의 `SET NX EX`

쿠폰 발급, 포인트 차감 등을 메시지 큐로 순차 처리:
- Kafka, RabbitMQ 활용
- 비동기 처리로 사용자 경험 개선
