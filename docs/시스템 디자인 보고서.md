## 개요

본 보고서는 이커머스 플랫폼의 핵심 기능인 **상품 랭킹 시스템**과 **선착순 쿠폰 비동기 발급 시스템**의 설계 및 개발 과정을 다룹니다.
두 시스템 모두 높은 트래픽과 동시성 문제를 해결하기 위해 Redis를 활용한 인메모리 처리 방식을 채택했습니다.

### 개발 목표
- **성능**: 대량의 동시 요청을 안정적으로 처리
- **정확성**: 데이터 정합성 보장 (중복 방지, 재고 관리)
- **확장성**: 시스템 부하에 따라 유연하게 확장 가능한 아키텍처
- **실시간성**: 사용자에게 실시간 정보 제공

- 주기적인 랭킹 데이터 집계 (5분마다)

#### 비기능 요구사항

### 3. 핵심 구현

#### 3.1 판매량 증가 (실시간 처리)
```java
@Override
public void increaseSales(Long productId, long quantity) {
    String dailyKey = dailyKey(LocalDate.now());

    // Redis Sorted Set의 score 증가
    redisTemplate.opsForZSet().incrementScore(
        dailyKey,
        productId.toString(),
        quantity
    );
}
```

**선택 이유**:
- Redis의 `ZINCRBY` 명령은 원자적(atomic) 연산으로 동시성 안전
- 인메모리 처리로 빠른 응답 시간 보장
- 별도의 락 없이도 정합성 유지

#### 3.2 랭킹 집계 (스케줄러)
```java
@Scheduled(cron = "0 */5 * * * *")
public void aggregateRanking() {
    aggregateProductRankingUseCase.aggregate(RankingPeriod.THREE_DAYS);
    aggregateProductRankingUseCase.aggregate(RankingPeriod.SEVEN_DAYS);
}
```

**집계 로직**:
```java
@Override
public void aggregate(RankingPeriod period) {
    LocalDate today = LocalDate.now();

    // 집계할 일별 키 목록 생성
    List<String> keys = switch (period) {
        case THREE_DAYS -> IntStream.range(0, 3)
                .mapToObj(i -> dailyKey(today.minusDays(i)))
                .toList();
        case SEVEN_DAYS -> IntStream.range(0, 7)
                .mapToObj(i -> dailyKey(today.minusDays(i)))
                .toList();
    };

    // Redis ZUNIONSTORE로 여러 날짜의 데이터 합산
    redisTemplate.opsForZSet().unionAndStore(
        existingKeys.get(0),
        existingKeys.subList(1, existingKeys.size()),
        destKey
    );
}
```

**최적화 포인트**:
- `ZUNIONSTORE`를 사용하여 O(N) 시간복잡도로 집계
- 존재하는 키만 필터링하여 불필요한 연산 방지
- 스케줄러로 주기적 집계하여 조회 시 부하 분산

#### 3.3 랭킹 조회
```java
@Override
public List<ProductRankingItem> findTopN(RankingPeriod period, int limit) {
    String key = getKeyForPeriod(period);

    // 상위 N개 조회 (내림차순)
    Set<ZSetOperations.TypedTuple<String>> tuples =
        redisTemplate.opsForZSet().reverseRangeWithScores(key, 0, limit - 1);

    // 결과 변환
    return tuples.stream()
        .map(tuple -> new ProductRankingItem(
            Long.valueOf(tuple.getValue()),
            tuple.getScore()
        ))
        .toList();
}
```

### 4. 성능 분석

#### 시간 복잡도
| 연산 | Redis 명령 | 시간 복잡도 |
|------|-----------|------------|
| 판매량 증가 | ZINCRBY | O(log N) |
| 랭킹 집계 | ZUNIONSTORE | O(N*K) |
| 상위 N개 조회 | ZREVRANGE | O(log N + M) |

**N**: Sorted Set의 요소 개수
**K**: 합칠 키의 개수
**M**: 조회할 요소 개수

#### 메모리 효율성
- 일별 데이터는 자연스럽게 날짜별로 분리되어 메모리 효율적
- 필요시 TTL 설정으로 오래된 데이터 자동 삭제 가능
- Sorted Set은 Skip List로 구현되어 메모리 효율적

### 1. 시스템 요구사항

#### 기능 요구사항
- 선착순 쿠폰 발급 (재고 제한)
- 사용자당 1회 발급 제한 (중복 방지)
- 비동기 처리로 빠른 응답 반환

#### 비기능 요구사항
- 초당 수천 건의 동시 요청 처리
- 재고 초과 발급 방지 (정합성)
- 중복 발급 방지
- 시스템 장애 시 데이터 복구 가능

```
2. 비동기 단계 (백그라운드)
   Scheduler → 큐 Poll → DB 저장 (0.1초마다)
```

### 3. 핵심 구현

#### 3.1 Redis 기반 선착순 체크
```java
public boolean tryAcquire(Long userId, Long couponId) {
    String issuedKey = "coupon:issued:" + couponId;
    String stockKey = "coupon:stock:" + couponId;

    // 1. 중복 체크 (Redis Set)
    Long added = redisTemplate.opsForSet().add(issuedKey, String.valueOf(userId));
    if (added == 0L) return false;  // 이미 발급받음

    // 2. 재고 감소 (Redis String)
    Long stock = redisTemplate.opsForValue().decrement(stockKey);
    if (stock < 0) {
        // 재고 부족 → 롤백
        redisTemplate.opsForValue().increment(stockKey);
        redisTemplate.opsForSet().remove(issuedKey, userId);
        return false;
    }

    return true;  // 발급 가능
}
```

**핵심 설계 포인트**:

1. **중복 방지 (Redis Set)**
   - `SADD` 명령은 이미 존재하는 요소는 추가하지 않음
   - 반환값 0 = 이미 존재 (중복), 1 = 새로 추가
   - 원자적 연산으로 동시성 안전

2. **재고 관리 (Redis String with DECR)**
   - `DECR`은 원자적 감소 연산
   - 음수 체크로 초과 발급 방지
   - 실패 시 롤백 로직 포함

3. **트랜잭션 없이도 정합성 보장**
   - Redis의 단일 명령은 원자적
   - 롤백 로직으로 일관성 유지

#### 3.2 비동기 이벤트 발행
```java
public void publish(Long userId, Long couponId) {
    String payload = userId + ":" + couponId;

    // Redis List를 큐로 활용
    redisTemplate.opsForList()
        .leftPush("coupon:issue:queue", payload);
}
```

**Redis List를 메시지 큐로 활용**:
- `LPUSH`: 큐의 왼쪽에 삽입 (Producer)
- `RPOP`: 큐의 오른쪽에서 꺼냄 (Consumer)
- FIFO 순서 보장

#### 3.3 비동기 Consumer
```java
@Scheduled(fixedDelay = 100)
public void consume() {
    // 1. 큐에서 메시지 Poll
    String payload = redisTemplate.opsForList()
        .rightPop("coupon:issue:queue");

    if (payload == null) {
        return;  // 큐가 비었음
    }

    // 2. 파싱
    String[] parts = payload.split(":");
    Long userId = Long.valueOf(parts[0]);
    Long couponId = Long.valueOf(parts[1]);

    // 3. 실제 DB 발급 처리
    try {
        issueCouponUseCase.execute(userId, couponId);
        log.info("쿠폰 발급 완료 - userId: {}, couponId: {}", userId, couponId);
    } catch (Exception e) {
        // 4. 실패 처리
        log.error("쿠폰 발급 실패 - userId: {}, couponId: {}, error: {}",
            userId, couponId, e.getMessage(), e);

        // Dead Letter Queue에 저장
        redisTemplate.opsForList().leftPush("coupon:issue:dead", payload);

        // 실패 카운트 증가
        String failCountKey = "coupon:fail:" + userId + ":" + couponId;
        redisTemplate.opsForValue().increment(failCountKey);
    }
}
```

**설계 특징**:

1. **폴링 방식**
   - 0.1초마다 큐를 확인하여 처리
   - CPU 효율적 (이벤트 없을 때는 즉시 리턴)

2. **에러 처리**
   - Dead Letter Queue: 실패한 메시지 별도 보관
   - 실패 카운트 추적: 모니터링 및 알림용
   - 로그 기록: 장애 추적

3. **확장성**
   - Consumer 인스턴스를 여러 개 실행하여 수평 확장 가능
   - 각 Consumer는 독립적으로 큐에서 메시지를 가져감

#### 3.4 Facade 패턴 적용
```java
public CouponInfo.CouponIssueResult issue(Long userId, Long couponId) {
    // 1. Redis 선착순 체크 (기존 코드 건드리지 않음)
    boolean ok = couponRedisService.tryAcquire(userId, couponId);

    if (!ok) {
        throw new IllegalStateException("선착순 마감 또는 중복 발급");
    }

    // 2. Redis에서 통과되면 기존 동기 코드 실행
    return issueCouponUseCase.execute(userId, couponId);
}
```

**Facade 패턴 선택 이유**:
- 기존 동기 로직(`IssueCouponUseCase`)을 수정하지 않음
- Redis 체크를 앞단에서 수행하는 Wrapper 역할
- 단일 책임 원칙 준수

## 회고

### 잘한 점

#### 1. Redis 활용

- **Sorted Set (랭킹)**: 자동 정렬로 O(log N) 성능
- **Set (중복 체크)**: 원자적 연산으로 안전한 중복 방지
- **String (재고)**: DECR로 동시성 제어
- **List (큐)**: FIFO 메시지 큐 구현

각 자료구조의 특성을 이해하고 활용하여 별도의 락 없이도 동시성 문제를 해결했습니다.

#### 2. 비동기 처리로 사용자 경험 개선
선착순 쿠폰 발급에서 비동기 처리를 도입하여:
- 사용자는 빠른 응답을 받고, 시스템은 안정적으로 처리

### 개선할 점

#### 1. 메시지 큐의 한계
현재 Redis List를 메시지 큐로 사용하고 있으나, 다음과 같은 한계가 있습니다:

**문제점**:
- Consumer가 메시지를 가져간 후 처리 실패 시 메시지 유실 위험
- At-least-once, Exactly-once 보장 어려움
- 메시지 우선순위 처리 불가

**개선 방안**:
```
RabbitMQ, Kafka 도입 검토
- 메시지 영속성 보장
- ACK 메커니즘으로 메시지 유실 방지
- 분산 처리 및 파티셔닝 지원
```

#### 2. Redis 장애 대응
Redis가 단일 장애점(SPOF)이 될 수 있습니다.

**현재 상황**:
- Redis 장애 시 쿠폰 발급 및 랭킹 조회 불가
- 데이터 유실 가능성

**개선 방안**:
```
1. Redis Sentinel 도입
   - 자동 Failover
   - 고가용성 확보

2. Redis Cluster 도입
   - 데이터 샤딩
   - 수평 확장

3. 백업 전략 수립
   - RDB 스냅샷
   - AOF 로그
   - 정기 백업
```

#### 3. 모니터링 및 알림 부재
현재는 로그만 남기고 있어, 실시간 모니터링이 어렵습니다.

**개선 방안**:
```
1. Metrics 수집
   - Prometheus + Grafana
   - 쿠폰 발급 성공/실패율
   - 큐 대기 메시지 수
   - 응답 시간 분포

2. 알림 설정
   - 실패율 임계치 초과 시 알림
   - 큐 적체 시 알림
   - Redis 메모리 사용량 알림

3. 분산 추적
   - Zipkin, Jaeger
   - 요청 전체 흐름 추적
```

#### 5. 랭킹 TTL 미설정
현재 랭킹 데이터에 TTL이 설정되어 있지 않아, 메모리가 계속 증가합니다.

**개선 방안**:
```java
// 일별 데이터는 7일 후 자동 삭제
redisTemplate.expire(dailyKey, Duration.ofDays(7));

// 또는 스케줄러로 오래된 키 정리
@Scheduled(cron = "0 0 2 * * *")  // 매일 새벽 2시
public void cleanupOldRankings() {
    LocalDate sevenDaysAgo = LocalDate.now().minusDays(7);
    String oldKey = dailyKey(sevenDaysAgo);
    redisTemplate.delete(oldKey);
}
```

### 배운 점

#### 1. 동시성 제어에 대한 이해
Lock을 사용하지 않고도 Redis의 원자적 연산으로 동시성을 제어할 수 있다는 것을 배웠습니다.
- CAS (Compare-And-Swap) 개념 이해
- 낙관적 vs 비관적 락의 트레이드오프
- 인메모리 DB의 성능 장점

#### 2. 비동기 처리의 중요성
모든 요청을 동기적으로 처리할 필요가 없다는 것을 깨달았습니다.
- 사용자 응답과 실제 처리를 분리
- 시스템 처리량과 응답 시간의 균형
- 이벤트 기반 아키텍처의 장점

#### 3. 적절한 도구 선택
문제에 맞는 도구를 선택하는 것이 중요합니다.
- 랭킹: Redis Sorted Set이 최적
- 재고: Redis String + DECR
- 메시지 큐: 간단한 경우 Redis List, 복잡하면 RabbitMQ/Kafka
